# Тест-стратегія: Merchant Payment Service (merchant-api:1.1)

## 1. Що тестували і чому (Обґрунтування зон тестування)

Об'єктом тестування є Docker-контейнеризований мікросервіс обробки платежів мерчанта, інтегрований із платіжним шлюзом Stripe (Sandbox) та базою даних PostgreSQL. 

Основні зони тестування та їх обґрунтування:
* **Життєвий цикл платежів (Payment Lifecycle):** Створення, підтвердження (`confirm: True`) та успішне проведення транзакцій. *Чому:* Це основна бізнес-цінність продукту; будь-який збій тут веде до втрати коштів мерчанта.
* **Операції повернення коштів (Refunds):** Повне та часткове повернення через вкладені ендпоінти (`/api/payments/{id}/refund`). *Чому:* Критичний функціонал для обслуговування клієнтів та дотримання фінансових норм.
* **Механізм ідемпотентності (Idempotency-Key):** Запобігання дублюванню транзакцій при повторних запитах. *Чому:* Захищає від випадкових подвійних списань у разі таймаутів або повторних кліків користувача.
* **Валідація даних та Edge Cases:** Перевірка поведінки системи на нульові/від'ємні суми (`amount = 0`, `amount < 0`), невалідні валюти та відсутність обов'язкових полів. *Чому:* Запобігає пошкодженню даних та забезпечує безпеку API від некоректних вхідних даних.
* **Інтеграція зі Stripe Sandbox:** Перевірка обробки відхилених карток (`pm_card_declined`) та недостатності коштів. *Чому:* Гарантує коректну реакцію сервісу на зовнішні помилки платіжного шлюзу.

---

## 2. Типи тестів та обґрунтування вибору

Для проєкту було обрано **автоматизовані інтеграційні API-тести** з використанням стеку `Python + pytest + requests`:

* **API Integration / Black-Box Testing:** 
  Тести взаємодіють із сервісом через HTTP-запити до запущеного через Docker середовища. *Чому:* Це дозволяє перевірити злагоджену роботу трьох компонентів разом: API-контролерів, бізнес-логіки та персистентності в PostgreSQL, імітуючи реальні запити клієнта.
* **Boundary Value & Negative Testing:** 
  Перевірка граничних значень (овер-рефанди, нульові суми) та відправка невалідних форматів. *Чому:* Дозволяє виявити дефекти валідації на ранніх етапах і гарантує, що система повертає безпечні коди помилок (`400`, `404`, `422`) замість критичних збоїв сервера (`500`).

## 3. Покриті ризики

За допомогою розробленого набору тестів та аналізу було закрито такі критичні ризики:

* **Фінансові ризики:**
  * *Подвійне списання коштів:* Закрито тестами ідемпотентності (де зафіксовано дефект `BUG-001` щодо відсутності обробки ключа).
  * *Овер-рефанд (збитки від повернення зайвих грошей):* Закрито граничним тестом на перевищення суми рефанду (зафіксовано критичний дефект `BUG-002`).
  * *Несанкціоновані суми:* Закрито негативними тестами на нульові та від'ємні суми платежів.
* **Технічні та інтеграційні ризики:**
  * *Цілісність бази даних:* Перевірено збереження станів транзакцій (`succeeded`) у PostgreSQL.
  * *Коректність обробки помилок шлюзу:* Перевірено реакцію на відхилені картки Stripe із поверненням відповідних статус-кодів.

---

## 4. Out of Scope (Що свідомо залишили поза межами)

Свідомо відокремлюючи пріоритети для поточного релізу, наступні компоненти не входили до scope тестування:

* **UI / Frontend Testing:** 
  Сторінка чекауту (`http://localhost:3000/checkout`) не тестувалася через браузерні автоматизаційні фреймворки. *Чому:* Основна логіка платежів та безпеки зосереджена на бекенд-API. Перевірка через API покриває фундаментальні ризики швидше і надійніше.
* **Load & Performance Testing:** 
  Стрес-тести на тисячі одночасних запитів (race conditions під високим навантаженням). *Чому:* Поточний етап фокусується на функціональній правильності бізнес-логіки базових сценаріїв та контрактів API (`merchant-api:1.1`).
* **Live Mode / Production Stripe Testing:** 
  Використання реальних банківських карток та реальних грошей. *Чому:* Виключено з міркувань безпеки та фінансових ризиків; всі тести виконуються виключно в тестовому середовищі Stripe Sandbox з використанням тестових токенів (`pm_card_visa`, `pm_card_declined`).
